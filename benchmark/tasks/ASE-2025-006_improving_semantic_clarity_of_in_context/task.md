# Task: ASE-2025-006 — Improving Semantic Clarity of In-Context Examples for LLM-based Unit Test Generation

## Background

Automated unit test generation is essential for software quality, and recent advances use large language models (LLMs) with in-context learning (ICL) to produce tests by providing examples. However, the effectiveness of ICL strongly depends on the semantic clarity of the example tests—clear, single-purpose tests with descriptive identifiers and comments foster better learning than “noisy” examples that mix multiple assertions or use ambiguous names. Existing developer-written and tool-generated tests often suffer from poor semantic clarity, and a prior refinement technique (UTgen) that aimed to improve textual clarity frequently degrades the original tests’ compilation success, pass rate, and coverage. Consequently, there is a critical need for a refinement approach that can systematically enhance both logical and textual clarity of unit tests while fully preserving their original testing effectiveness, thereby unlocking the full potential of ICL-based test generation.

## Research Question

How can unit tests be transformed to increase their semantic clarity (logical and textual) while maintaining their original test coverage and correctness, and what is the impact of these refined tests on the quality of tests generated by in-context learning approaches?

### Baselines
```
- name: Origin (unrefined unit tests)
  reference: No specific tool; represents original developer-written or tool-generated tests without refinement.

  reference: A prior LLM-based test refinement technique that improves textual clarity; referenced as [6] in the original paper.
- name: RAGGen (test generation)
  reference: Retrieval-Augmented Generation approach for unit test generation; cited as [4] in the original paper.

  reference: Counter-example enhanced test generation approach; cited as [5] in the original paper.
```

### Metrics
```
- name: Compilation Success Rate (CSR)
  definition: Percentage of generated or refined tests that compile successfully.
- name: Pass Rate (PR)
  definition: Percentage of tests that execute and pass against the focal method without failures.
- name: Line Coverage (Cov)
  definition: Average percentage of lines covered by a test suite across focal methods, measured with a coverage tool (e.g., Cobertura).
- name: Mutation Score (MS)
  definition: Proportion of artificially injected faults (mutants) that the test suite successfully detects, as per standard mutation testing.
- name: Semantic Clarity Rank
  definition: In a user study, participants rank refined tests on conciseness, descriptiveness of identifiers, and comment quality; a lower rank indicates better clarity.
```

### Sub-questions
```
- RQ1: How effective is the refinement technique in preserving test effectiveness (CSR, PR, Cov, MS) and improving semantic clarity compared to unrefined and UTgen-refined tests?
- RQ2: To what extent does using refined tests as in-context examples improve the test generation performance (CSR, PR, Cov) of the RAGGen and TELPA approaches?
```

### Target Subject

Real-world Java projects with JUnit test suites. Open-source examples: projects from the Defects4J benchmark (e.g., Chart, Time). Industrial examples: three proprietary systems (a program analysis toolkit, a microservice, and a data analysis framework). Both developer-written and automatically generated (via EvoSuite) tests are considered.

### Constraints

The refinement must not degrade the original test suite's compilation, passing behavior, coverage, or mutation score. For industrial projects, Java 17+ may prevent EvoSuite-based generation, so only developer-written tests may be used. Experiments require an accessible LLM (e.g., DeepSeek-V2.5 or similar) and GPU hardware for test generation runs (the original study used multiple NVIDIA A800 GPUs). Integrating refined examples into RAGGen and TELPA implies dependencies on those tools' artifacts.

## Feasibility Notes

Open-source datasets (Defects4J) and tools (EvoSuite, Cobertura) are publicly available, enabling reproduction on the non-industrial portion. Industrial datasets are private, restricting external validation. The full pipeline (refinement + test generation + coverage/mutation analysis) requires significant GPU resources and time; using smaller open-source LLMs could lower costs. The user study represents a substantial manual effort; an automated substitute based on code metrics would be possible but may not fully capture semantic clarity.
