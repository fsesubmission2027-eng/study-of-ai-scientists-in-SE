# Task: FSE-2025-002 — Assessing Noise in Unit Test Generation Training Data and Its Impact on LLM Performance

## Background

Unit testing is critical for software reliability, but manually writing high-quality tests is labor-intensive. Traditional automated test generation tools like Randoop and EvoSuite produce tests based on code analysis. Recent learning-based approaches leverage LLMs fine-tuned on large datasets of focal methods and test cases to generate unit tests. However, the quality of these training datasets has been largely ignored, despite known issues with noise in other software engineering tasks. Noise in test generation data—such as syntax errors, irrelevant test cases, or low-coverage examples—can impair model performance, yet no systematic study has characterized the prevalence and impact of such noise. Given the unique requirements of generating executable tests with high coverage, understanding and mitigating noise in this domain is essential.

## Research Question

What types of noise exist in large-scale unit test generation datasets, and to what extent does removing such noise improve the quality of tests generated by LLMs?

## Experiment Setup

### Datasets
```
- name: Methods2Test
  source: GitHub: microsoft/methods2test
  description: A large dataset of Java focal methods and their corresponding developer-written JUnit test cases, commonly used for training test generation models.
  access: open
- name: Atlas
  source: contact authors of Atlas dataset [65]
  description: Another large-scale dataset of Java methods and test cases, used alongside Methods2Test for training LLMs.
  access: restricted (available upon request)
- name: Defects4J
  source: GitHub: rjust/defects4j
  description: A benchmark of 835 real bugs from 17 Java projects, used to evaluate test generation quality. 757 focal methods and 1,440 test cases are extracted after removing projects where test naming conventions differ.
  access: open
```

### Baselines
```
- name: Randoop
  reference: Pacheco et al., "Randoop: feedback-directed random testing for Java", OOPSLA 2007
- name: EvoSuite
  reference: Fraser and Arcuri, "EvoSuite: automatic test suite generation for object-oriented software", ESEC/FSE 2011
- name: CodeBERT
  reference: Feng et al., "CodeBERT: A Pre-Trained Model for Programming and Natural Languages", EMNLP 2020
- name: AthenaTest (replicated with CodeT5)
  reference: Tufano et al., "Unit Test Case Generation with Transformers and Focal Context", arXiv 2020 (AthenaTest)
- name: StarCoder
  reference: Li et al., "StarCoder: may the source be with you!", TMLR 2023
- name: CodeLlama7B
  reference: Roziere et al., "Code Llama: Open Foundation Models for Code", arXiv 2023
```

### Metrics
```
- name: CodeBLEU
  definition: Combines n-gram match (BLEU), syntactic AST similarity, and data-flow similarity to compare generated code with reference code; weight 0.25 for each component.
- name: Syntactic Correctness Rate
  definition: Percentage of generated test cases that parse correctly according to Java syntax using a tree-sitter parser.
- name: Compilation Passing Rate
  definition: Percentage of generated test cases that compile and execute without runtime errors when run with JUnit.
- name: Line Coverage
  definition: Average percentage of lines of the focal method executed by the generated test suite.
- name: Branch Coverage
  definition: Average percentage of branches in the focal method exercised by the generated test suite.
```

### Sub-questions
```
- RQ1: What is the prevalence and distribution of noise types in the Methods2Test and Atlas datasets?
- RQ2: How does removing noise from training data affect the performance (CodeBLEU, compilation rate, line coverage, branch coverage) of LLM-based test generators?
- RQ3: How do different categories of noise contribute to degradation in test generation quality?
```

### Target Subject

Java projects with JUnit test suites taken from open-source repositories. Specifically, the focal methods and test cases in the Methods2Test and Atlas training corpora, and the Defects4J benchmark (17 Java projects, e.g., JFreeChart, Google Gson).

### Constraints

Training and hyperparameter splits use 80/20 random partitions. To avoid data leakage, any focal method whose name matches a method in the Defects4J validation set is removed from training. Maximum input sequence length for LLMs is 1024 tokens; longer inputs are truncated. Training follows the original hyperparameters of each LLM (e.g., learning rate 1e-5, batch size 8, LoRA settings for large models). Inference uses greedy decoding. All experiments run on four NVIDIA A800 GPUs.

## Feasibility Notes

The training datasets are publicly available (Methods2Test) or accessible on request (Atlas). Fine-tuning large LLMs like StarCoder and CodeLlama7B requires substantial GPU memory; smaller models such as CodeBERT can be fine-tuned with fewer resources. Constructing a noise taxonomy may require manual inspection and expert validation, but once defined, automated filtering can be implemented. The overall task is computationally intensive but feasible with appropriate hardware.
