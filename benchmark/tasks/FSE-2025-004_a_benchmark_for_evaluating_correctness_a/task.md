# Task: FSE-2025-004 — A Benchmark for Evaluating Correctness and Time Efficiency of AI-Generated Code

## Background

Large language models (LLMs) are increasingly used to generate code from natural language instructions, but current evaluation benchmarks focus solely on correctness (i.e., passing small test cases). Time efficiency is critical for real-world software, yet existing correctness benchmarks use small inputs that cannot distinguish efficient from inefficient solutions, and wall-clock execution time measurements are unstable across machines. There is a pressing need for a benchmark that can reliably assess both the correctness and the time efficiency of LLM-generated code.

## Research Question

How can a benchmark be designed to enable stable, comprehensive evaluation of both correctness and time efficiency of LLM-generated code solutions?

## Experiment Setup

### Datasets
```
- name: Code Efficiency Benchmark
  source: Built on top of HumanEval (https://github.com/openai/human-eval), MBPP (https://github.com/google-research/google-research/tree/master/mbpp), CodeContests (https://github.com/google-deepmind/code_contests), and APPS (https://github.com/hendrycks/apps). The final augmented benchmark will be released on GitHub.
  description: Contains 398 function-level and 358 file‑level Python programming problems. Each problem includes original correctness test cases, new stressful test cases with very large inputs, and a ground truth solution.
  access: open (upon release)
```

### Baselines
```
- name: EvalPlus test-case mutation
  reference: Liu et al., "Is Your Code Generated by ChatGPT Really Correct? Rigorous Evaluation of Large Language Models for Code Generation" (2023)
- name: Direct LLM-based stressful test case generation
  reference: Prompting an LLM (e.g., GPT-4) to directly generate test cases with extremely large inputs, without additional validation or contract guidance.
- name: Execution time metric (baseline for stability)
  reference: Standard wall-clock execution time measurement using Python's `time` module, repeated multiple times on a fixed machine.
```

### Metrics
```
- name: pass@k
  definition: Probability that at least one of the top k generated code solutions passes all correctness test cases.
- name: Execution time
  definition: Wall-clock time taken by a code solution to process a stressful test case, averaged over multiple runs.
- name: CPU instruction count
  definition: Number of CPU instructions executed by the code solution as measured by hardware performance counters (e.g., `perf stat`).
- name: efficient@k
  definition: Fraction of problems where at least one of the top k generated solutions is both correct (passes all test cases) and has CPU instruction count within a small tolerance factor (e.g., 10%) of the ground truth solution's instruction count.
```

### Sub-questions
```
- RQ1: To what extent do stressful test cases (with large inputs) improve the distinguishability of time efficiency among different code solutions compared to standard small test cases?
- RQ2: How does the stability of CPU instruction count measurements compare to that of execution time measurements across repeated runs?
- RQ3: How does the ranking of popular LLMs change when evaluated using efficient@k versus pass@k alone?
```

### Target Subject

Python code generation tasks from existing correctness benchmarks (HumanEval, MBPP, CodeContests, APPS), spanning function-level and file-level, competition-style problems. The solutions are generated by LLMs and must be both correct and time-efficient.

### Constraints

The benchmark must use test cases that can distinguish different time complexities without requiring candidate solutions to be executed during test case generation (to avoid prohibitive runtime). The efficiency metric must be stable across different machines; if CPU instruction count is used, `perf` support is required. Stressful test cases should have inputs large enough to produce measurable differences in execution time but not so large that execution becomes impractical within a few seconds.

## Feasibility Notes

Existing correctness benchmarks are publicly available. Generating stressful test cases may require querying LLM APIs (e.g., GPT-4), which incurs cost. Measuring CPU instruction counts needs a Linux environment with `perf`; executing all generated solutions on standard GPU servers or via APIs is feasible. The main challenge is automatically generating valid stressful test cases that correctly respect input constraints and are large enough to differentiate time complexity without executing the candidate solutions.
